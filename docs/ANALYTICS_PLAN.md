# Analytics v1: обнаружение, хронология и чтение инцидентов

## Зачем модуль

Analytics — слой Detect. Он превращает опубликованные события LogParser в
проверяемые инциденты: какая VM превысила порог, почему сработало правило и
какие строки это доказывают.

Парсер не решает, что аномалия. UI и LLM не ищут сбои. На OpenStack из Loghub
«сбой» — нарушение времени создания VM, не уровень ERROR: в abnormal-файле
ERROR нет, в нормальных файлах они есть. Рабочий сигнал — поле
`build_duration_seconds`.

План опирается на [исследование](RESEARCH.md) §5.3 и текущий модуль
[Analytics](../src/Analytics/README.md). Reasoning, поиск похожих эпизодов и
подключение UI — отдельные задачи.

## Исходное состояние

Уже есть: чистая функция `slow_vm_build`, CLI `detect` над JSONL, отчёт v1 и
тесты без сети. Детектор принимает итератор событий и не зависит от источника.

Сохранить без изменений:

- команда `detect --input --dataset-id --threshold-seconds`;
- JSON-отчёт v1 и коды `0` / `1` / `2`;
- группировка `(source_sha256, instance_id)`, максимум длительности,
  строгое превышение порога, выбор evidence при равенстве, стабильный
  `incident_id`, ранжирование по `excess_seconds`.

Порог по умолчанию не появляется. `27.91` — пример из исследования
(`max(normal1) + 5`), не зашитое значение.

## Объём v1

Один класс аномалий, пакетный запуск, один писатель.

```text
опубликованные log_events
        ↓
явный порог или baseline
        ↓
slow_vm_build
        ↓
этапы allocate → image → spawn → build
        ↓
таблицы incidents / incident_evidence
        ↓
чтение через CLI-отчёт или API
```

| Делаем | Не делаем |
|---|---|
| Чтение `log_events` для зафиксированных загрузок | Оценка по `anomaly_labels.txt`, команда `evaluate`, `/evaluation` |
| Явный baseline или явный порог | Подбор порога по оцениваемому входу; детектор по ERROR/шаблонам |
| Одна карточка на `(source_sha256, instance_id)` | Слияние UUID из разных файлов; фиктивный `unknown` |
| Этапы и `evidence_ids` той же VM | Связь по request ID или только по времени |
| Повторяемая публикация инцидентов | Живой таймер незавершённого build |
| Чтение списка, карточки, timeline и строки | LLM-гипотезы, search, MCP-чат, контейнер Analytics, health |

Метки, имена `normal`/`abnormal` и ERROR не входят в признаки и не пишутся в
карточку. Сравнение с ERROR-baseline — материал демо, не второе правило.

## Реализация

### 1. Чтение опубликованных событий

Добавить HTTP-адаптер ClickHouse с настройками `CLICKHOUSE_*` и
параметризованными запросами. Формат строк — `JSONEachRow`. Внутренности
пакета LogParser не импортировать.

В начале `run` зафиксировать срез `current_ingestions` выбранного
`dataset_id`. Читать только эти `ingestion_run_id`. Если во время чтения
публикация сменилась — ошибка, без частичного результата.

Для детектора достаточно проекции `BuildEvent`. Для хронологии нужна более
широкая запись: `event_id`, набор, источник, время, компонент, `instance_id`,
сообщение, длительности `build`/`spawn`, `parse_status`. Шаблоны Drain3 в
правилах не использовать.

JSONL-адаптер и `detect` остаются для локальной проверки правила.

### 2. Порог и обнаружение

Порог задаётся одним из двух способов, не смешивать в одном запуске:

- `--threshold-seconds`, как сейчас;
- `--reference-source` и `--margin-seconds`:
  `threshold = max(build_duration_seconds на reference) + margin`.

Reference — явно выбранные `source_sha256` внутри того же `dataset_id`.
Пустой reference без завершённых VM — ошибка. Для воспроизведения исследования:
`openstack_normal1.log` и запас `5`.

Baseline сохранять рядом с запуском: источники, запас, вычисленный порог,
число завершённых и неполных VM, медиана и максимум. Это снимок расчёта, не
обучаемая модель.

Правило `slow_vm_build` не менять. Незавершённые VM считать отдельно и не
превращать в инциденты. `excess_seconds` — величина отклонения, не вероятность
причины.

### 3. Этапы одной VM

После выбора маркера завершения восстановить ленту
**allocate → image → spawn → build** по той же паре
`(source_sha256, instance_id)`.

Распознавать этапы по числовым полям и версионируемым правилам над компонентом
и текстом сообщения. Не привязывать правила к `template_id`.

Граница эпизода — выбранный маркер build. Предыдущие завершения той же VM и
последующее уничтожение не включать. События без `instance_id` не доклеивать.

Сортировка: `event_time` (UTC, исходная точность), затем номер строки,
затем `event_id`. Записи без времени — отдельным списком, не вставлять в
середину ленты.

Для каждого этапа: найден или нет, измеренная длительность если есть,
`evidence_ids`. Пропуск обозначать явно. `build_duration_seconds` и
`spawn_duration_seconds` не складывать: интервалы перекрываются.

Модуль фиксирует наблюдение и полноту данных. Причину задержки и уверенность
в диагнозе не выводит. Если нет spawn-строки, срабатывание по build
сохраняется, полнота помечается как неполная.

### 4. Публикация

Собственные объекты Analytics в той же базе, по образцу LogParser:
попытка в raw-таблицах и представление последней завершённой публикации
(`incidents`, `incident_evidence`).

Один `run` обрабатывает все зафиксированные источники выбранного набора.
Версия запуска зависит от входных загрузок, порога либо baseline, версии
детектора и правил этапов.

Писать полностью, затем ставить отметку завершения. Пока отметки нет,
результат не виден в представлениях и API. Повтор того же завершённого входа
возвращает существующий запуск. После сбоя — новая попытка, не дописывание.

В доказательстве хранить `event_id` и `ingestion_run_id` снимка. Новая загрузка
LogParser не должна менять уже опубликованную карточку: API читает снимок
запуска, не «текущие» события источника.

Новый успешный запуск заменяет текущую выборку, в том числе когда инцидентов
ноль.

## Интерфейсы

Две команды сверх существующего `detect`:

| Команда | Назначение |
|---|---|
| `run` | ClickHouse → порог или baseline → детектор → этапы → публикация |
| `serve` | Чтение опубликованных представлений |

Схему применять в начале `run` и `serve`, отдельную команду `migrate` не
вводить. `fit-baseline` не выделять: расчёт baseline — часть `run`.

`run` печатает тот же отчёт v1, что и `detect`, плюс `analysis_run_id` и
этапы у каждой карточки. Поля и алгоритм `incident_id` не меняются.

API только читает. Расчёт запускается командой `run`, не HTTP-методом.

| Endpoint | Результат |
|---|---|
| `GET /v1/incidents?dataset_id=…` | Ранжированные карточки текущего запуска |
| `GET /v1/incidents/{id}` | Порог, наблюдение, baseline, этапы, полнота |
| `GET /v1/incidents/{id}/timeline` | События эпизода и `evidence_ids` этапов |
| `GET /v1/events/{id}` | Снимок строки из доказательств этого запуска |

Набор из четырёх срабатываний в одну страницу не разбивать. Ошибки: `404`
если нет объекта или публикации, `422` если нет `dataset_id` или ID некорректен,
`503` если нет схемы или БД.

Зависимость HTTP-сервера — отдельная optional-группа установки. Пакет без неё
должен выполнять `detect` и `run`.

## Приёмка

- Текущие тесты `detect` и коды завершения остаются зелёными.
- Синтетика: граница порога, группировка по источнику, устойчивость evidence,
  неполные VM, пустой и битый ввод, пустой reference, смена публикации во
  время чтения, повтор `run`, замена выборки нулевым результатом.
- Этапы: чужой UUID в другом файле не попадает в ленту; несколько завершений
  не склеиваются; нет spawn — неполнота при сохранённом инциденте.
- Архив OpenStack, если доступен: reference `normal1`, запас 5 с, оценка
  `normal2 + abnormal`. Ожидание аудита — 1 510 завершённых VM, три неполных
  наблюдения, четыре срабатывания при пороге 27,91 с. У VM 51,59 с в ленте
  есть spawn 50,72 с.
- Сквозной путь: импорт LogParser → `run` → карточка API → исходная строка
  по `event_id`.

Четыре метки — воспроизведение разведки, не промышленная оценка. В README
модуля зафиксировать: пакетный режим, неизменяемый снимок запуска,
обнаружение после завершения VM, один локальный писатель.
