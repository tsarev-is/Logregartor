# Analytics

Отдельный Python-модуль детерминированного обнаружения аномалий OpenStack.
Начальная версия читает JSONL от LogParser и выдаёт JSON-отчёт с инцидентами.
Вычисления выполняются независимо от UI и LLM.

## Запуск

Нужен Python 3.11+. Сторонних зависимостей для выполнения нет.
Из корня репозитория:

```bash
cd src/Analytics
python3 -m log_analytics --help
python3 -m log_analytics detect \
  --input ../LogParser/output/openstack/events.jsonl \
  --dataset-id openstack \
  --threshold-seconds 27.91
```

Входной JSONL создаётся командой `pipeline run` или `pipeline transform`
из [LogParser](../LogParser/README.md). Допустим и результат `parse`: первое
правило использует числовые признаки, шаблоны ему не нужны. Поля события
соответствуют [LogParser v1](../LogParser/schema/log-event.v1.json).
Проверяются необходимые детектору поля; полная проверка схемы, хеша источника
и manifest остаётся обязанностью конвейера LogParser.

`27.91` — пример порога из [исследования](../../docs/RESEARCH.md), подобранный
ретроспективно на небольшом наборе. Значения по умолчанию нет: порог передаётся
явно. Автоматическое обучение baseline ещё не реализовано.

Успех возвращает код `0` и один JSON-отчёт в stdout. Ошибка чтения, формата или
конфигурации возвращает код `1` и сообщение в stderr, без частичного отчёта.
Некорректные аргументы CLI возвращают код `2`.

При необходимости установите CLI в виртуальное окружение:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
logregartor-analytics --version
```

## Первое правило: slow_vm_build

- Анализируется только явно выбранный `dataset_id`.
- Для каждой пары `(source_sha256, instance_id)` выбирается максимальное
  `build_duration_seconds`. Одинаковые UUID из разных файлов не объединяются.
- Инцидент создаётся при строгом превышении порога; ранжирование — по величине
  превышения в секундах. Это не вероятность причины сбоя.
- `evidence_ids` содержит ID строки с выбранной длительностью. При равенстве
  длительностей выбирается максимальный `event_id`, независимо от порядка входа.
- VM без маркера завершения учитывается в `incomplete_instances` и не становится
  автоматически аномалией. Записи без явного `instance_id` не группируются.
- Уровень ERROR, название файла и оценочные метки не участвуют в решении.
- Детектор срабатывает после завершения создания VM; живой таймер не реализован.

`Incident` содержит стабильный ID, набор и источник, VM, имя и версию детектора,
время доказательства, наблюдаемую длительность, порог, превышение и evidence ID.
ID зависит от набора, источника, VM и класса аномалии. Повторный запуск сохраняет
ID; изменение порога меняет результат правила, но не идентичность той же карточки.
Хронология, гипотезы о причинах и состояние объяснения ещё не входят в контракт.

## Структура

```text
log_analytics/
  cli.py                       # CLI и сериализация результата
  config.py                    # Явные параметры правила
  models.py                    # BuildEvent, Incident, DetectionReport
  jsonl.py                     # Чтение событий из локального файла
  detectors/build_duration.py  # Чистая функция детектора
tests/                         # Проверки правила и CLI
pyproject.toml                 # Python-пакет и команда CLI
```

## Проверки

Из `src/Analytics`:

```bash
python3 -m unittest discover -s tests -v
```

Тесты используют синтетические записи, без ClickHouse, сети и модели.
Они проверяют границу порога, группировку и ранжирование, устойчивость evidence,
неполные наблюдения, пустой и повреждённый ввод. Качество на реальном архиве
этими тестами не измеряется.
