# Analytics

Python-модуль детерминированного обнаружения аномалий OpenStack по
[плану Analytics v1](../../docs/ANALYTICS_PLAN.md). Читает JSONL или опубликованные
события LogParser в ClickHouse, обнаруживает медленное создание VM,
восстанавливает этапы и публикует инциденты с доказательствами.
Вычисления выполняются независимо от UI и LLM.

Это **пакетный режим**, **обнаружение после завершения VM**, **неизменяемый
снимок запуска** и **один локальный писатель**. Живого таймера незавершённых
операций, диагностики причин, вероятности диагноза и обучения модели нет.

## Установка и локальный detect

Нужен Python 3.11+; `detect` и `run` используют только стандартную библиотеку.
Из корня репозитория:

```bash
cd src/Analytics
python3 -m log_analytics --help
python3 -m log_analytics detect \
  --input ../LogParser/output/openstack/events.jsonl \
  --dataset-id openstack \
  --threshold-seconds 27.91
```

JSONL создаётся командами `pipeline run`, `pipeline transform` или `parse`
из [LogParser](../LogParser/README.md). Проверяются необходимые детектору поля
[LogParser v1](../LogParser/schema/log-event.v1.json); полная проверка схемы,
хеша источника и manifest остаётся обязанностью конвейера LogParser.

CLI можно установить в виртуальное окружение:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
logregartor-analytics --version
```

Успех `detect` и `run` возвращает код `0` и один JSON-отчёт в stdout.
Ошибка чтения, формата, конфигурации или БД возвращает `1` и сообщение в stderr,
без частичного отчёта. Некорректные аргументы CLI возвращают `2`.
Контракт `detect`, JSON-отчёт v1 и алгоритм `incident_id` сохранены.

## ClickHouse: run

Сначала опубликуйте вход через LogParser. `run` анализирует **все** источники
выбранного `dataset_id`, зафиксированные в `current_ingestions` в начале запуска.
Набор без опубликованных загрузок — ошибка; опубликованный пустой файл допустим.

```bash
python -m log_analytics run --dataset-id openstack --threshold-seconds 27.91
```

Альтернатива — явно выбранный baseline: максимум завершённого build на reference
плюс запас. `--reference-source` принимает SHA-256 содержимого файла, а не имя;
флаг повторяется для нескольких источников того же набора.

```bash
python -m log_analytics run \
  --dataset-id openstack \
  --reference-source 4e4d47347bdae198056bb3b0a8a755e1cb0100d6c6a30bbd4058684234769199 \
  --margin-seconds 5
```

Это хеш `openstack_normal1.log` из закреплённого архива. Reference можно выбрать
из `current_ingestions` или взять `source_sha256` из отчёта LogParser.
Baseline и явный порог нельзя смешивать; margin обязателен и неотрицателен.
Reference вне набора либо без завершённых VM отклоняется. Порог должен быть
конечным и положительным. **Порога по умолчанию нет.** `27.91` — воспроизведение
[исследования](../../docs/RESEARCH.md), а не встроенная настройка.

В отчёт и каждую карточку записывается baseline: хеши reference, запас, порог,
число завершённых и неполных VM, медиана и максимум длительности. Статистика
считается по максимуму каждой пары `(source_sha256, instance_id)`. Reference
также входит в общие счётчики `run`, поскольку запуск обрабатывает весь набор.

`run` добавляет к отчёту v1 `analysis_run_id`, `analysis_version`,
`input_ingestions`, `baseline`, `stage_rules_version` и этапы у каждой карточки.

### Настройки подключения

Окружение совпадает с настройками HTTP-клиента LogParser; его Python-пакет
не импортируется.

| Переменная | Значение по умолчанию |
| --- | --- |
| `CLICKHOUSE_URL` | `http://localhost:8123` |
| `CLICKHOUSE_DB` | `logs` |
| `CLICKHOUSE_USER` | `logregartor` |
| `CLICKHOUSE_PASSWORD` | `localdev` |
| `CLICKHOUSE_TIMEOUT` | `60` секунд |

Экспортируйте переменные перед запуском: модуль не читает `.env` автоматически.
При изменении порта Compose измените и `CLICKHOUSE_URL`.
Секреты не передавайте в URL или аргументах команды. HTTP-адаптер использует
[параметризованные запросы и JSONEachRow](https://clickhouse.com/docs/interfaces/http),
проверяет ответ целиком и не повторяет INSERT при потере соединения.

### Публикация и восстановление

`run` и `serve` применяют [собственную SQL-схему](log_analytics/sql/001_initial.sql)
через `IF NOT EXISTS`. Схему LogParser создаёт его загрузчик.
Отдельной команды `migrate` нет. Пользователю БД нужны права на создание объектов
при старте; HTTP-запросы API выполняют только чтение.

- `analysis_runs` хранит состояния `started` / `completed`, снимок входных загрузок,
  конфигурацию, версию и отчёт.
- `incidents_raw` и `incident_evidence_raw` хранят отдельные попытки публикации.
  Доказательства содержат `event_id`, исходный `ingestion_run_id` и копию строки.
- `current_analysis_runs`, `incidents`, `incident_evidence` показывают только
  последнюю завершённую публикацию каждого набора.

После записи карточек и доказательств проверяются количество и уникальность
строк; только затем ставится `completed`. Изменение публикации LogParser во
время чтения или перед завершением запуска прерывает попытку. Предыдущий результат
остаётся видимым. Новая успешная публикация заменяет всю выборку, **включая
результат с нулём инцидентов**.

Версия зависит от набора и зафиксированных загрузок, порога либо baseline,
версий детектора, этапов и формата запуска. Повтор завершённого входа возвращает
тот же `analysis_run_id`, в том числе после потери ответа на финальный INSERT.
При возвращении к ранее завершённой конфигурации её снимок становится текущим
с сохранением ID. После сбоя незавершённой попытки создаётся новый UUID;
частичные строки не дописываются.

Локальный `flock` запрещает одновременных писателей с тем же URL и базой.
Это не распределённая блокировка: используйте один хост и одинаковые настройки
подключения для запусков. История и незавершённые raw-попытки сохраняются;
автоматической очистки нет. Переимпорт LogParser не меняет опубликованные карточки.

## Правило и этапы VM

- Детектор анализирует только выбранный `dataset_id`.
- Для каждой пары `(source_sha256, instance_id)` выбирается максимум
  `build_duration_seconds`; UUID из разных файлов не объединяются.
- Инцидент создаётся при **строгом** превышении порога. Ранжирование — по
  `excess_seconds`, затем `incident_id`. Отклонение не является вероятностью причины.
- При равенстве длительностей выбирается максимальный `event_id` независимо от
  порядка входа. `evidence_ids` карточки по-прежнему содержит выбранный build.
- VM без завершения учитываются в `incomplete_instances`, без создания инцидента.
  Записи без явного `instance_id` не группируются.
- ERROR, имя файла, оценочные метки и `template_id` не участвуют в решении.
  Имя источника доступно только в снимках строк для навигации.

`incident_id` зависит от набора, источника, VM и класса аномалии; изменение порога
меняет решение, но не идентичность той же карточки.

Лента `allocate → image → spawn → build` ограничена выбранным завершением и
предыдущим маркером build этой VM. Последующие уничтожения не входят в эпизод.
Правила [stages.py](log_analytics/stages.py) версионируются отдельно: числовые
build/spawn, сообщения claim в `nova.compute.claims/resource_tracker`, подготовка
образа в `nova.virt.libvirt.*`, успешный spawn в driver/manager.

Каждый этап содержит `name`, `found`, `duration_seconds` (или `null`),
`evidence_ids`. Измеренные build и spawn **не складываются**: интервалы
перекрываются. Отсутствующий этап, проблемы разбора и строки без времени отражаются
в `completeness`; отсутствие spawn не отменяет инцидент по build.

События сортируются по времени UTC с сохранением наносекунд, номеру строки и ID.
`undated_events` идут отдельно и ограничиваются номерами строк между завершениями.
Если выбранный build не имеет времени, границы всего эпизода определяются номерами
строк. Степень полноты описывает наблюдения, а не уверенность в диагнозе.

## API: serve

HTTP-сервер устанавливается отдельной optional-группой; она не нужна `detect`/`run`.

```bash
python -m pip install -e '.[api]'
python -m log_analytics serve --host 127.0.0.1 --port 8080
```

| Endpoint | Результат |
| --- | --- |
| `GET /v1/incidents?dataset_id=openstack` | Отчёт текущего запуска с ранжированным массивом `incidents`, без пагинации |
| `GET /v1/incidents/{id}` | Карточка: наблюдение, порог, baseline, этапы, полнота, ID запуска |
| `GET /v1/incidents/{id}/timeline` | `events`, `undated_events`, этапы с evidence ID, полнота |
| `GET /v1/events/{id}` | Копия строки из доказательств, включая `raw_text`, `line_ending`, `ingestion_run_id` |

Для карточки, timeline и строки можно передать `?analysis_run_id=<UUID>`.
Это фиксирует навигацию на завершённом снимке, даже если новый запуск Analytics
уже заменил текущую выборку. Передавайте ID из списка/карточки во все следующие
запросы. Без этого параметра читается текущая публикация. Если одна строка входит
в несколько наборов, `/events/{id}` требует `analysis_run_id`, чтобы снять
неоднозначность. Незавершённые попытки недоступны даже по явному UUID.

Ошибки: `404` — объект или публикация отсутствует; `422` — нет `dataset_id`,
некорректен ID либо ссылка на строку неоднозначна; `503` — БД или схема недоступна;
`405` — метод кроме GET. Расчёты выполняются только CLI-командой `run`.

## Проверки

Из `src/Analytics`, без БД и сети:

```bash
python3 -m unittest discover -s tests -v
```

Синтетические тесты покрывают прежний `detect`, baseline, UTC/наносекунды,
границы эпизодов, пропуски этапов, изоляцию источников, повреждённый ввод,
смену загрузки, скрытые попытки, повтор запуска, нулевую замену, API и коды CLI.

Сквозные тесты используют **новую временную базу**, удаляемую по завершении.
Нужны работающий ClickHouse, Go и Python с зависимостями LogParser. Можно
передать `LOGPARSER_BINARY` и `LOGPARSER_PYTHON`; иначе используются сборка Go
и текущий Python. Тест HTTP требует установленной группы `.[api]`.

```bash
ANALYTICS_CLICKHOUSE_TEST=1 \
LOGPARSER_PYTHON=../LogParser/.venv/bin/python \
python -m unittest discover -s tests -p test_clickhouse_integration.py -v
```

Для полного архива дополнительно задайте `LOGPARSER_DATA_DIR` — абсолютный путь
к каталогу трёх логов после `pipeline prepare`. Проверяется настоящий путь
LogParser CLI → ClickHouse → baseline/run → карточка/timeline → исходная строка.
На `normal2 + abnormal` ожидаются 1 510 завершённых VM, три неполных наблюдения,
четыре срабатывания при пороге 27,91 с; у VM с build 51,59 с — spawn 50,72 с.
Сам `run` также включает reference в общие счётчики. Это воспроизведение аудита
малого архива, а не промышленная оценка качества.

Reasoning, поиск похожих эпизодов и подключение UI — отдельные задачи.
